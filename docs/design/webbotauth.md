Architected 2026-08-05 against HEAD `3828b64`, as the stage-A deliverable of
`docs/design/tier2.md` §7 part 3. Decision-complete: every load-bearing call is

## 0. What this is, and what premise it replaces

RFC 9421 HTTP Message Signatures, profiled by the Web Bot Auth architecture
draft (draft-meunier-web-bot-auth-architecture): an automated agent signs its
requests with a private key and names, in a `Signature-Agent` header, an HTTPS
directory where the matching public key is published. An origin that fetches
the directory can verify that traffic *claiming* to be that agent *is* that
agent.

This project rejected the anti-detect premise early (security.md,
"Fingerprinting: consistency, not randomness"; tier2 §6 item #3's demotion).
Web Bot Auth is the same decision from the other side: **rather than hiding
that a bot is driving, prove which bot it is.** The capability being built
here is identification, not evasion, and §8 makes that binding on the
implementation rather than leaving it as tone.

Context that sharpens why the *client-side* capability is the right half to
own: the head-to-head found the incumbent's own README steering users toward
CLI+skills driving local browsers as its recommended token-efficient path
(h2h-evaluation.md §7.5). The agent-browsing population is consolidating on
exactly the shape Aperture is — a user's own machine, the user's own sessions —
which is exactly the population the hosted-operator enrollment model does not
serve. Building the signing capability now, scoped to what a personal browser
can honestly claim, is what makes Aperture able to participate the day the
ecosystem grows a user-scale story, and immediately useful against origins the
user already controls.

## 1. The deadline and the enrollment half — ruled dead, now with the policy text in hand

Tier2 §7 part 1 killed "registered signed agent before 2026-09-15" as an
Aperture goal on two grounds: the date is Cloudflare's rollout date for
hosted operators, not a registration cutoff; and a project key shipped inside
every install is public, therefore worthless-to-hostile. Tier2 required this
document to check that ruling against Cloudflare's actual enrollment
requirements rather than inference. Checked, 2026-08-05:

- **Cloudflare's signed-agents policy excludes this product on its face.**
  The published policy requires that "the service must be made for widespread
  use of zones — a bot crawling one site is not valid," plus a publicly
  documented purpose and a user-agent registered to the service. A personal
  browser, one install per human, each with its own key, fails the
  widespread-use requirement *per key*, and the alternative — one shared
  project key — fails custody (§2). There is no per-user enrollment path in
  the published policy. **Part 1 is therefore not revisited; it is
  corroborated.** If Cloudflare later publishes a per-user or
  per-install enrollment story, THIS file is where the ruling gets reopened.
- **What exists instead, today:** any origin the user controls can verify
  self-hosted keys — Cloudflare's own open-source `web-bot-auth` library
  (signer + verifier, TypeScript) runs in a Worker or any Node process, and
  the well-known directory convention
  (`/.well-known/http-message-signatures-directory`) is a static JSON file the
  user can host anywhere. That is the verifier population this design serves:
  the user's own origins, their LAN services, and any site whose operator
  chooses to trust the user's directory.

The 2026-09-15 date appears nowhere else in this file. It is someone else's
deadline.

## 2. Key custody, honestly

**The question:** what does Aperture sign with, given that a key in a
client-distributed browser is not a secret against the machine's own user, and
a key shared across installs is not a secret at all?

**The ruling: a per-container Ed25519 keypair, generated by Aperture on the
user's machine, never imported, never exported in private form, never shared
across installs or containers.** In detail, each with its WHY:

1. **No project key, ever.** Shipped = public = the first abuser signs as
   "Aperture" and burns the identity for every install. This is tier2's
   ruling; it is structural, not situational, and no amount of obfuscation
   changes it. Nothing in this design creates, fetches, or embeds any key
   that did not originate on this machine.
2. **Generated, not imported.** The other direction — the user generates a
   key elsewhere and pastes the private JWK into Aperture — is refused. Every
   imported key is a key that existed somewhere else, transited something,
   and now has two homes; the feature's entire cost is a second code path
   plus a standing invitation to move private keys through chat windows. The
   user who wants the same identity in two places is asking for a custody
   story that does not exist (that is tier2's finding, from the other side).
   One install, one container, one key. The PUBLIC half is exported freely —
   that is the point of it.
3. **Per-container, not per-install.** §5 argues this fully; the custody
   consequence is that compromise or burn of one container's identity never
   touches another's.
4. **Stored in `userData/botauth/<containerId>.key.json`, plaintext JWK, file
   mode 0o600 (the `mcp.json` precedent — Windows ACLs make the mode largely
   symbolic, and saying otherwise would be theater).** NOT inside the vault,
   deliberately: the vault idle-locks after five minutes, and a signing key
   coupled to vault state produces an identity that flickers — signed
   traffic, then unsigned, then signed, within one session on one origin.
   The fingerprint doctrine's whole lesson is that *inconsistency* is the
   loudest signal there is; an intermittent identity assertion is worse for
   the user than a readable key file. The threat that reads the file —
   same-user local code execution — is out of envelope by security.md's
   opening section and already owns the vault's plaintext lifetime, the MCP
   bearer token, and the browser itself. What such an adversary GAINS here is
   impersonation of this container's agent identity until the user
   unpublishes the public key from their directory — and "edit a JSON file
   you host" is the revocation story, stated as such.
5. **The private key never leaves the main process.** No IPC channel, no MCP
   tool, no log line, no error message carries it. The load-bearing property
   from security.md — no agent-facing response type has a field that can
   carry a secret — extends to this key: no type in the MCP response union
   gains a key-shaped field, and `test/botauth.test.ts` asserts the module
   surface (§7).

**What an unverifiable key is still good for — answered, because the honest
answer shapes the whole feature.** A signature nobody can look up proves only
same-signer continuity, and to every origin that cannot verify it, the
`Signature-Agent` header plus a stable `keyid` is nothing but a supercookie —
a globally unique tracking beacon volunteered on every signed request. That
is worse than nothing for a privacy-first browser. **Therefore: no directory
URL configured ⇒ signing is structurally off** — not defaulted off, not
warned about: the predicate (§3) cannot pass without one, so there is no
configuration in which Aperture emits an unverifiable identity assertion.
With a directory URL configured, the key is verifiable by construction — by
exactly the origins the user tells about it — and the smaller-but-real thing
this design builds is: **"identify my agent, cryptographically, to origins I
choose."** The registration/reputation half stays not-ours (§1).

## 3. What gets signed, and when

Signing marks traffic as agent traffic. Emitted indiscriminately it (a) leaks
that an agent is driving to origins that never asked — a fingerprinting
decision, and the containers doctrine forbids volunteering identity — and (b)
hands page script a signature-minting oracle. The scope rule exists to make
both impossible by construction rather than unlikely by intent.

**A request is signed iff ALL of the following hold.** The predicate is a
pure function of configuration, tab state, and the request — never of any
response, never of any page-supplied string (§8 for why that is load-bearing):

| # | condition | why |
|---|---|---|
| S1 | The request's target matches an entry in the **container's allowlist** (§6 config): a registrable-domain entry matched via `registrableDomain()` (the vault's own function — punycode, PSL + supplemental, fail-closed on `null`), or an exact-origin entry (`http://…`/`https://…`) matched via `originOf()` equality. Exact-origin entries exist because `registrableDomain()` correctly returns `null` for IP literals and single-label hosts, and the local-verifier probe, LAN boxes, and dev servers live there. **A `null` from `registrableDomain()` matches nothing** — two IP-literal origins must never pool in a null bucket (the exact failure `originOf`'s header warns about). | The human names every origin that ever learns the agent's identity. Nothing is volunteered. Subdomain reach of a domain entry is the same operator by PSL rules — `github.io` tenants stay separate automatically because the private section splits them. |
| S2 | The request is a **main-frame document request** (`resourceType === 'mainFrame'`). | This is the single sharpest cut in the design. It makes `fetch()`/XHR/img/script/iframe requests unsignable, which closes the minting oracle: page script on an allowlisted origin (the needle mechanism's own adversary — injected script on an honest origin) cannot manufacture signed requests with chosen method/path/body by calling `fetch()`. It also means a third-party page embedding resources FROM an allowlisted domain cannot cause signed subresource traffic to it. What remains page-triggerable is a top-level navigation (`location.href`), which is loud — the tab visibly leaves the page, refs invalidate, the agent sees it — and is bounded by S1's allowlist. Deployed verification today evaluates the document request; §10 defers subresource signing behind a named trigger. |
| S3 | The tab is **`agentOwned`** — created through the MCP surface. | `agentOwned` is the one agent/human boundary that already exists, is already shown to the human (the tab strip marks agent tabs), and already gates `browser_capture`. The alternatives are all dishonest at request granularity: "harness-initiated navigations only" cannot be distinguished from page-initiated ones at the `webRequest` layer once `browser_act` clicks a link (both are renderer-initiated), and a boundary that cannot be implemented honestly produces a signature that sometimes lies. An agent-owned tab's whole activity is agent-session activity — including server redirects and page-side redirects of that session — which is exactly what a hosted agent's egress signs. |
| S4 | The tab's **container** has signing configured: directory URL present, key present, container not ephemeral, no config error (§5, §6). | §2's "no directory, no signature" plus §5's container rulings, enforced in one place. |

**Consequences, stated so nobody discovers them as surprises:**

- **Human tabs are never signed** — even on allowlisted domains, even while
  the agent drives them via default-`tabId` tools. A Web Bot Auth signature
  asserts "automated agent traffic"; a human's tab is shared authorship, and
  a false bot assertion on human browsing is the anti-detect lie inverted —
  the doctrine ("never lie about something whose lie has an observable
  correlate you cannot also fake") cuts against false claims in BOTH
  directions. Corollary: an agent working in the human's tab on an
  allowlisted origin gets unsigned traffic and may be challenged by that
  origin; the remedy is `browser_tabs action:"open"` — the agent gets its own
  tab, which is where the product wants agent work anyway.
- **Popups are not signed.** `setWindowOpenHandler` creates children with
  `agentOwned` defaulting false, and this design leaves that untouched: a
  page-initiated `window.open` is the page's act, not the agent's, and
  making popups inherit `agentOwned` would silently widen `browser_capture`'s
  allowed set too — that flag is now load-bearing twice over, and G33d's
  second sabotage row exists to keep it that way.
- **Redirects re-decide.** Each hop of a redirect chain is a fresh request
  through `onBeforeSendHeaders`: a hop that leaves the allowlist is unsigned
  automatically, a hop within it gets a fresh signature. No state is carried.
- **Signing never depends on a response.** No "detect the block page and
  retry signed" (adaptive evasion-shaped, and a page-controlled identity
  trigger), and RFC 9421 §5.1 `Accept-Signature` is **ignored entirely** — on
  allowlisted origins we already sign proactively, and off-allowlist a
  response header must not be able to solicit an identity disclosure.
- **The residual, exactly:** page script on an allowlisted origin, running in
  an agent-owned tab, can trigger signed top-level GETs (or form-POSTs) to
  chosen paths on allowlisted domains, and a captured signature replays
  against the same method+path+authority until `expires` (created+300 s,
  §4) on a verifier that does not enforce nonce uniqueness. Bounded by: the
  human chose those domains; the navigation is loud; covered components pin
  method and path so a harvested signature is useless anywhere else; the
  nonce lets any verifier that cares close replay entirely. Stated as a
  residual, not closed.

## 4. The wire format, pinned

One signature, label `sig1`, over covered components:

```
("@authority" "@method" "@path" "signature-agent")
```

with signature parameters `created` (now, integer seconds), `expires`
(created + 300), `keyid` (base64url RFC 7638 JWK thumbprint, computed over
the OKP members `{crv,kty,x}` per RFC 8037 A.3), `tag="web-bot-auth"`, and
`nonce` (64 CSPRNG bytes, base64url, `crypto.randomBytes` — never
`Math.random`, the envelope-nonce house rule). Headers emitted:
`Signature-Input`, `Signature`, `Signature-Agent` (value: the container's
directory URL). Ed25519 (`ed25519` per RFC 9421 §3.3.7), via `node:crypto` —
**zero new production dependencies**, and Ed25519 signing is deterministic
(RFC 8032), which §7's vectors exploit.

WHY these components and not the draft minimum: the architecture draft
requires only `@authority` or `@target-uri` plus created/expires/keyid/tag,
and requires that when `Signature-Agent` is sent it is covered. Covering
`@method` and `@path` as well narrows every harvested signature to the exact
request shape it was minted for (§3 residual) at zero protocol cost. 300 s
is far inside the draft's ≤24 h recommendation; a signature is consumed
within one network round trip, and each redirect hop gets a fresh one, so
nothing needs a long window.

**The one fact this file cannot pin from here, handled by procedure rather
than by guess:** the `Signature-Agent` value's exact structured-field form is
in motion across draft revisions (early revisions: a bare quoted sf-string;
the current draft's examples: an sf-dictionary member key-linked to the
signature label, covered as `"signature-agent";key="sig1"`), and Cloudflare's
docs state their deployment does not support every RFC 9421 component. So the
builder MUST, at implementation time: pin the latest release of Cloudflare's
`web-bot-auth` npm package in the probe (§7.3, probe-local dependency only);
byte-compare our signature base against that library's signer for the same
request; adopt the `Signature-Agent` form it emits; and if its verifier
rejects the four-component list, fall back to
`("@authority" "signature-agent")` — same parameters — and record which form
shipped, with the library version and draft revision, in security.md. That is
a decision procedure with one ordered fallback, not a choice left open.

## 5. Interaction with identity containers — ruled

A container is the unit of identity in this product; the only rotation
primitive is a new container. A signed identity that leaks across containers
would let every allowlisted origin do what the fingerprint work exists to
prevent. Four rulings:

1. **The keypair is per-container.** Two containers never share a key, so no
   origin ever sees the same `keyid` from two containers. Structural, not
   configurable.
2. **The directory URL is per-container, and one directory URL may appear in
   at most ONE container's config.** The `Signature-Agent` VALUE is itself an
   identifier: two containers sending the same directory URL are linkable by
   any origin allowlisted in both, which defeats the container boundary
   through a side door the per-container keys had closed. A duplicate is a
   config error: signing disables for **both** containers involved, loudly,
   at load (fail closed — the alternative, picking a winner, silently
   grants one container an identity the human ambiguously assigned). The
   user who genuinely wants one identity in two containers hosts the same
   JWKS at two URLs — a real cost that makes the linkage deliberate.
3. **Ephemeral containers refuse signing.** An ephemeral container is the
   maximal-unlinkability primitive; a persistent identity assertion inside
   one is a contradiction. Config naming an ephemeral container is an error
   for that entry, logged at load, signing off for it.
4. **Agent-created containers change nothing.** `browser_container` lets the
   agent create a container with a chosen id; if that id happens to be one
   the human configured for signing, the agent has merely instantiated the
   container the human already ruled on — traffic is still signed only to
   the human's allowlisted domains with the human's configured identity. No
   new authority flows. (Stated because someone will ask; the predicate
   needs no extra clause.)

Key lifecycle follows the container id: keys are generated at startup for
every validly configured container (not lazily per request — the signing path
does no I/O and no generation), persist across launches under the container
id, and rotation is manual: delete `<containerId>.key.json`, restart, a fresh
key generates, republish the directory. Automated rotation is deferred (§10).

## 6. The user's control surface

This is a privacy-first browser whose owner uses it personally. Signing is an
identity assertion, so enabling it must be a deliberate human act, and no
part of it may be agent-reachable.

**The control is a human-edited config file** — `userData/botauth.json`, read
once at startup (restart to apply; a live file-watcher is a new
write-to-behavior channel with no demonstrated need):

```json
{
  "version": 1,
  "containers": {
    "default": {
      "directoryUrl": "https://bots.example.net",
      "sign": ["example.com", "https://tools.example.net", "http://10.0.0.199:8080"]
    }
  }
}
```

- `directoryUrl`: HTTPS required in file config (the seeded dev path, §7.4,
  may carry loopback HTTP; real config may not).
- `sign`: registrable-domain entries and/or exact-origin entries (§3 S1). A
  domain entry must equal its own `registrableDomain()` (punycode) — an entry
  like `www.example.com`, which is a host and not a registrable domain, is a
  config error for that entry, logged with the canonical form it should be.
  Silently canonicalizing would make the file claim something the human did
  not write.
- Parse/validation failures **fail closed per entry** — a bad container entry
  disables signing for that container with a loud console line naming the
  reason; an unparseable file disables signing everywhere, loudly; the
  browser always starts. A config error must never be quieter than the
  feature it disables.

**What it costs the human, stated honestly:** editing a JSON file, restarting
the browser, and hosting a static JWKS at
`https://<their-host>/.well-known/http-message-signatures-directory` (the
directory draft additionally expects the directory response itself to carry a
signature — Cloudflare's `web-bot-auth` tooling includes directory-serving
helpers; hosting is the user's job and out of Aperture's scope). This is a
power-user feature and this control surface says so. A settings UI is
deferred (§10) rather than half-built.

**What Aperture does to help:** on generating (or loading) a key for a
configured container it writes
`userData/botauth/<containerId>.directory.json` — a ready-to-publish JWKS
containing the public key — and logs, per signing-enabled container, one
startup line: container name, key thumbprint, directory URL, allowlist. Those
lines are the human's audit surface; the tab strip's existing agent-tab
marking already shows *which* tabs can produce signed traffic.

**The agent surface is zero.** No MCP tool reads, writes, enables, disables,
or reports signing config; no tool result names the key, the thumbprint, the
directory URL, or the allowlist; the tool count does not change. The
allowlist in particular is withheld — handing a manipulable agent a list of
"origins where this browser will assert identity" is a targeting map for
injected content, and it costs nothing to withhold. (The agent can infer
signing from an origin's behavior; it cannot enumerate it.) Config and key
files are outside every agent-reachable write path — the egress enumeration
gains rulings for the two new `writeFile` sites (§7.5), both "paths Aperture
builds, under userData," the vault's own class.

### 7.3 The local verifier — proving correctness with no cooperating verifier in the wild

Two independent instruments, deliberately of different authorship:

- **`bench/probes/webbotauth/`** (standalone, own `package.json`, the ONLY
  place Cloudflare's `web-bot-auth` npm package is depended on — the product
  dependency set does not change): the §4 differential probe. Signs a fixed
  request with our leaf and with the library; byte-compares bases; verifies
  ours with their verifier and theirs with our bench verifier. Run once at
  implementation; results (library version, draft revision, which
  `Signature-Agent` form shipped) recorded in security.md's queue table and
  RESULTS.md.
- **A bench verifier written from the RFC, in `bench/probes/webbotauth/verify.mjs`,
  imported by `bench/guards.mjs`** — a second implementation that shares no
  code with `src/net/` (the point: our implementation must not be verified
  solely by itself). Its own acceptance, before it may judge anything: it
  verifies the RFC B.2.6 example (a signature produced by neither
  implementation) and rejects a mutated copy of it. It parses
  `Signature-Input`/`Signature` off the wire, rebuilds the base from the raw
  request line and headers, `crypto.verify`s against the published JWKS,
  and enforces `created`/`expires`/`tag`/`keyid`-lookup — G33e exists to
  prove it can say no (see the sabotage table for why "can say no" includes
  staleness, not just tampering).

The guard run starts this verifier as an in-process HTTP server on
**port 8902** (8901 is the WebAuthn probe's; 8817/8894/8896/8898/8899 are the
bench's and are never touched), serving: a fixture page; the JWKS at the
well-known path; and a per-request verdict recorded server-side and rendered
into the next fixture page load so a `browser_snapshot` can read it. The same
server is reachable as two origins — `http://127.0.0.1:8902` (allowlisted)
and `http://localhost:8902` (not) — which is what lets G33b run its control
with zero extra infrastructure.

## 8. What this must NOT do — binding, not tone

1. **Signing is identification, never evasion.** No code path may vary any
   fingerprint surface (UA, client hints, headers beyond the three signature
   headers, timing) based on signing state; `useragent.ts` and the UA
   coherence guarantees are untouched. The config file's documented purpose
   and the security.md paragraph the builder adds must both state: this
   feature tells chosen origins the agent's identity; it does not, and must
   never be extended to, get the agent PAST anything. A future PR that keys
   any evasion behavior off this module re-litigates the project's founding
   rejection and must be refused on that ground.
2. **Signature headers are additive.** The mux contract (§7.1) forbids
   deleting or rewriting any header. The residual — whether Chromium
   re-serializes header order/casing when `onBeforeSendHeaders` returns
   modified headers — is queue #7, measured at implementation (§9), and
   whatever the answer, it is scoped to origins the user already chose to
   identify to, which is why it is disclosable rather than blocking.
3. **No response-driven signing, no `Accept-Signature`, no block-page
   retry** (§3). The predicate reads config, tab, and request. Nothing a
   server or page emits can turn signing on, off, or re-aim it.
4. **Nothing agent-reachable** (§6). The agent can neither cause an identity
   assertion the human did not configure, nor enumerate where assertions
   happen, nor learn key material. The one thing an agent CAN do — drive
   signed traffic to allowlisted domains from its own tabs — is the feature.

## 9. Acceptance — RED first, then green, then the battery

**Ordering rule:** no green counts until its red has been observed. The unit
tests are written before the leaf exists (vectors and predicate matrix
against stubs: RED), the G33 block is run once against the pre-feature
artifact, and each guard's sabotage rows are applied, run, observed RED, and
reverted, with the guard runner's artifact hash recorded per row (the
`bench/guards.mjs` header convention).

**The vacuity trap, handled structurally:** G33b/c/d assert *absence* of
signatures, so against a pre-feature build they would pass vacuously. The
G33 block therefore hard-fails every leg when G33a (presence) is not green in
the same run — the `G30-seed` pattern: a missing precondition reads as RED,
never as a block of quiet passes.

## 10. What this deliberately does not include — and what is deferred rather than built

- **Enrollment on Cloudflare's public Signed Agents list.** Dead, with the
  policy text in hand (§1). Not deferred — not ours. Reopens in this file
  only if a per-user enrollment path is published.
- **Subresource and subframe signing.** Excluded by S2 for the §3 reasons.
  Deferred behind a named trigger: a verifier the user actually faces
  demonstrably requiring signed subresources. The change is one predicate
  clause plus a re-run of the §3 minting analysis — which is the part that
  must be redone, not skipped, because S2 is currently what closes the
  `fetch()` oracle.
- **A settings UI.** The config file is the control surface (§6). Deferred
  until a second kind of user exists; a half-UI would put an identity toggle
  somewhere the owner does not look.
- **Key rotation automation, `nbf`/`exp` directory metadata management.**
  Manual rotation is specified (§5); automation is bookkeeping on top of a
  custody story that works without it.
- **`Accept-Signature` reactive signing.** Ruled out, not deferred (§3, §8).
- **Signing human browsing as the human.** A different feature with a
  different name (user identity assertion), explicitly out: this design's
  honesty rests on the signature meaning "automated agent," and S3 is that
  meaning.
- **Debugger-attach detectability (queue #3)** stays queued with its tier2
  trigger; nothing here moves it.
- **Should any of the built part be deferred instead?** Considered, and no:
  the build is small (one pure leaf, two wiring files, one mux), it closes
  queue #4 by construction as a side effect, and every risky surface it
  touches is behind guards that have sabotage rows. The one piece that
  WOULD have argued for deferral — a mandatory external dependency or a
  protocol still too fluid to pin — was eliminated by the §4 differential
  procedure and the zero-dependency ruling. If the differential probe finds
  Cloudflare's library and the draft irreconcilable with our component set
  even after the fallback, THAT is the deferral trigger: ship nothing,
  record the incompatibility here, and wait for the draft to settle rather
  than shipping a signature nobody can verify.

## 11. Deviations from tier2 §7 part 2's sketch — named, so a reviewer can tell a decision from drift

Tier2 §7 part 2 sketched the implementation in six lines and delegated the
design here. Four of its clauses are changed by this file, on purpose, and
this section is the record (the same rule tier2 §0 applied to its own brief):

1. **"Per install" → per-container** (§5). The sketch predates the brief's
   container question; one key across containers hands every allowlisted
   origin a cross-container correlator, which is the exact thing the
   container work exists to prevent.
2. **"Stored beside the vault material" → plaintext JWK under
   `userData/botauth/`, outside the vault** (§2.4). Vault coupling makes the
   identity flicker with the five-minute idle lock; an intermittent
   assertion is a louder anomaly than a key file the out-of-envelope
   adversary could read anyway.
3. **Covered components gain `"signature-agent"`** (§4). The draft mandates
   covering the header when it is sent; the sketch's
   `@authority`/`@method`/`@path` list predates that reading.
4. **Scope: "navigations and subresource loads in a tab while an MCP-driven
   session is acting on it" → main-frame documents in `agentOwned` tabs
   only** (§3). The sketch's subresource clause reopens the `fetch()`
   minting oracle S2 closes, and its session phrasing ("while … acting on
   it") is not implementable honestly at the `webRequest` layer — S3 is the
   crisp boundary that already exists and is already shown to the human.

`docs/HANDOFF.md`'s §7 summary repeats the per-install and
subresource wording; the builder's HANDOFF edit (§7.5) corrects both to
match this file.

### 12.2 Item two — which `Signature-Agent` form and component list shipped

**Shipped: the legacy sf-string form.**

```
Signature-Agent: "http://127.0.0.1:8902"
Signature-Input: sig1=("@authority" "@method" "@path" "signature-agent")
                 ;created=…;expires=…;keyid="…";tag="web-bot-auth";nonce="…"
Signature:       sig1=:…:
```

Component list `("@authority" "@method" "@path" "signature-agent")` — **§4's
ordered fallback did not fire**: Cloudflare's verifier accepts the
four-component list (probe D7, D8). Parameters are §4's enumeration in §4's
order — `created, expires, keyid, tag, nonce` — with **no `alg`**: §4 does not
list it, the algorithm is determined by the key the directory publishes, RFC
9421 §7.3.7 warns against a verifier trusting it, and the probe measures that
Cloudflare's verifier does not require it.

**§4 said to adopt the form the library emits. It does, and three independent
measurements say the same thing — the third being one this document could not
have anticipated:**

1. **The library emits sf-string and cannot verify sf-dict.** Its
   `REQUEST_COMPONENTS` is `["@authority", "signature-agent"]` — bare, no
   `;key=`. Worse, for a component that DOES carry parameters its base builder
   hands over the whole header value (`sig1="https://…"`) instead of the named
   member (`"https://…"`), so it computes a base nobody else computes. Probe
   D10 asserts that rejection, and goes RED the day the library is fixed.
2. **draft-05 prefers sf-dict and marks sf-string LEGACY** ("THIS IS A LEGACY
   EXAMPLE. IF YOU ARE AN IMPLEMENTER, PLEASE UPDATE TO THE ABOVE"). v04's
   changelog is where the header became an sf-dictionary.
3. **draft-05's own Ed25519 vector for the preferred form is internally
   inconsistent, and that is a finding about the draft rather than about us.**
   Appendix A.2.2 prints a base whose signature-agent line is
   `"signature-agent";key="agent2": "https://signature-agent.test"` and
   publishes a signature that **does not verify against it**. Re-signing the
   printed base with the draft's own key (RFC 9421 B.1.4) gives different
   bytes. The signature DOES verify against the same base with the member value
   **unquoted** — measured, probe row D2b. Appendix A.2.1 (no signature-agent)
   and A.2.3 (legacy sf-string) are both self-consistent and both reproduced by
   our leaf byte for byte, base and signature.

So the draft-preferred spelling currently has **three readings in the wild** —
the draft's printed base, the draft's published signature, and the reference
library — and no vector that settles which is right. Shipping it would be
choosing one of three and hoping. **Both forms are implemented** in
`botAuthCore.ts` behind `SHIPPED_SIGNATURE_AGENT_FORM`, each with its own
external vector in the probe, so moving is a one-constant change with a
measurement on either side of it. D10 and D2b are the tripwires: either goes
RED when the ecosystem moves, and that is when §4's decision procedure gets
re-run.

**One divergence recorded rather than fixed.** The draft (§4.2.2) specifies a
base64url nonce and Aperture emits one. The library's `validateNonce` decodes
with `atob`, which is standard base64 and rejects `-` and `_`; roughly 93% of
64 random bytes produce at least one. It bites only on THEIR signing path —
their verifier never inspects the nonce — which is why D7 passes with a
base64url nonce end to end. Recorded as probe row D11.

**Verification vectors reproduced, all from primary sources rather than from
this file:** RFC 9421 B.2.6 base byte-exact and signature bytes exact (Ed25519
is deterministic, so this is an equality, not a roundtrip); RFC 8037 A.3
thumbprint exact; draft-05 A.2.3 base and signature exact; A.2.2 base exact.
Our thumbprint equals the library's `keyid` for the same key, our
`@signature-params` line is byte-identical to the library's for the same
ordered parameters, and our signature bytes are identical to the library's for
the same request (probe D1–D6).

### 12.6 Amendments — three, all narrowing, none of them silent

§7.5 requires deviations to be written HERE before the code lands. Three, and
the first is a factual correction to a premise this document states twice.

**1. `registrableDomain()` does not return `null` for IP literals and
single-label hosts. It returns the HOST.** §3 S1 says exact-origin entries exist
"because `registrableDomain()` correctly returns `null` for IP literals and
single-label hosts". Measured against `src/vault/vault.ts` at this tree:

```
http://127.0.0.1:8902  ->  "127.0.0.1"     http://localhost:8902    ->  "localhost"
http://[::1]:8902      ->  "[::1]"         https://a.b.notarealtld  ->  null
```

The vault's own comment says why — *"literal addresses have no registrable
domain; they are their own identity."* Two consequences, one repaired and one
recorded:

- **Repaired, failing closed.** A bare `127.0.0.1` in `sign` would have passed
  §6's "must equal its own `registrableDomain()`" check and then matched at
  DOMAIN granularity — every port and BOTH schemes on that address, strictly
  wider than the exact-origin entry the human meant and wider than anything §3
  sanctions. The config validator now refuses an address literal or a
  single-label host as a domain entry, naming the exact-origin spelling to use
  instead. This narrows; it never widens.
- **Recorded: §9's G33b author-independent sabotage row cannot be built as
  written.** The row is "route exact-origin entries through
  `registrableDomain()` for uniformity: both `127.0.0.1` and `localhost` yield
  `null`, a null-equality or null-bucket fallback matches them to each other,
  localhost signs → RED." Under that exact refactor `127.0.0.1` and `localhost`
  yield `"127.0.0.1"` and `"localhost"` — **distinct, so the guard's control
  stays GREEN and the row proves nothing.** That inability is itself the
  finding, and it is reported rather than papered over.

  **The CLASS still bites, one granularity up, and is guarded.** The same
  tidiness refactor throws away the SCHEME and the PORT, so an exact-origin
  entry starts matching `http://127.0.0.1:9999` and `https://127.0.0.1:8902`.
  That instance is constructible, is in the matrix, and was measured RED as
  **S-W6**. And the genuine null-pooling hazard the row was reaching for is
  real for a different input class — two unknown-suffix hosts both yield `null`
  — so `matchesAllowlist` refuses a `null` on every path and the matrix asserts
  it with `a.b.notarealtld` against `c.d.alsonotreal`.

**2. Config validation lives in the pure leaf, not in `botAuth.ts`.** §7.1 puts
"config load/validation" in `botAuth.ts`; §7.2 item 5 requires the suite to
exercise every §6 failure mode, and the suite cannot import `botAuth.ts`
because it imports `electron`. The two clauses cannot both hold. Resolved in
favour of the testable one: `parseBotAuthConfig` (pure, in `botAuthCore.ts`)
makes every §5/§6 decision and returns `{config, errors}`; `botAuth.ts` does
the I/O and the logging. No ruling changed — only which file it can be executed
in.

**3. `test/egress.test.ts` gained a third receiver class, `WebRequest`.** §7.5
scopes the builder to "ruling rows only" there. A ruling row for
`.onBeforeSendHeaders` would have been STALE the moment it was written, because
that member is reached through the `Session#webRequest` accessor and the
guard's two receiver patterns (annotation, direct binding) cannot follow an
accessor. So the enumeration was **widened** — `Session` and `WebContents`
became `Session`, `WebContents` and `WebRequest` — and nothing was narrowed, no
existing regex was touched, and no existing ruling changed. The alternative was
a table that claimed to rule on something it could not see, which is the failure
mode that file's guard section exists to prevent.
